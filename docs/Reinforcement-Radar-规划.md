# Reinforcement Radar — 规划文档

版本：草案 v1 ｜ 日期：2026-10-01 ｜ 状态：**待你审阅**

## 1. 为什么要做一个新的

现成的 `mods/hd2_local/automaton_reinforcement_cd` v0.1.2 已经跑通了，而且在你机器上实测有效：

```
status=COOLDOWN   authoritative=true   seconds=171
raw_remaining=164.014862   fraction=0.911190   rate=0.963457   pending=0
```

`seconds = ceil(164.01 / 0.963457) = 171`，和它代码里的公式完全吻合。**这套读取路径是经过实机验证的，我不打算重新发明它。**

但我有三个理由写自己的版本：

**它的 HUD 依赖小地图打开。** 代码里 `byte(P.mission_active)~=1 or ... or byte(P.map_widget+P.open)~=1 then return {shown=false, reason='minimap closed'}`——小地图没开就整条隐藏。你的日志里 `minimap_shown=false` 正是这个状态。**而你想知道"还有多久拉烟"的时刻，通常正是没在看地图的时候。**

**它只做 Automaton。** 模块名就是 `automaton_reinforcement_cd`。但要确认过它内部读的是"当前任务的原生共享增援冷却"（`scope = "current mission native shared enemy reinforcement cooldown"`），配了 `factions = {Terminid, Automaton, Illuminate}`——**冷却机制本身是共享的，所以扩到全部派系成本很低**，只是它没做。

**它的实现以纯文本嵌入，不可改。** 它把 18677 字节 Lua 源码直接塞在资源体里（这也是我能完整读出来的原因）。要改任何东西都得重新嵌一遍。

**所以：读取逻辑照搬它验证过的方案，HUD 和扩展重新做。**

---

## 2. 目标

**核心**：在任务中随时看到敌人增援冷却状态与精确倒计时，不依赖小地图。

**明确的非目标**（除非你要加）：
- 不写游戏内存（全程只读，与 CD mod 一致）
- 不做联网、不影响其他玩家
- 不检测"正在拉烟"这个事件本身（那是另一个数据源，需要再探测）

## 3. 功能设计

### 3.1 主显示

| 状态 | 显示 | 颜色 |
| --- | --- | --- |
| `READY` | `REINFORCEMENT READY` / `可拉烟` | 绿 |
| `COOLDOWN` | `REINFORCEMENT 02:51` | 橙 |
| `PENDING` | `REQUEST QUEUED` | 橙 |
| `PAUSED` | `COOLDOWN PAUSED` | 灰 |
| 非权威端 | 比例条 / `SYNC` | 灰 |
| 不在任务 | 隐藏 | — |

**关键差异：不绑小地图。** 地图开不开都显示。

### 3.2 位置：右上角，任务目标面板下方（你的反馈 1）

实机截图确认了目标区域：右上角是原生任务目标面板（标题 + 若干子目标行），HUD 贴在它下沿。

**实现分两步走，先能看再对齐：**

**第一步（本次实施）**：用屏幕分辨率百分比定位，先用固定值试（按截图比例估算：右上角、约 x=0.78w、y=0.13h），并**输出实际分辨率与坐标到日志**，方便我据实调整。

**第二步（可选，需再跑一次实机）**：**读取任务目标面板的真实几何**，像 CD mod 读小地图那样：

```lua
-- CD mod 已验证的模式：从全局根 + 控件偏移读出 panel 矩形
local a = root + P.map_widget + P.panel
local data = S.read(a, 160)          -- 内含 x/y/width/height/scale
```

小地图的偏移已知，但**任务目标面板的偏移未知，需要先做一次探测**。这一步的收益是 HUD 会精确贴合面板下沿、随面板显隐自动跟随，而不是靠固定坐标硬凑。

### 3.3 关于读取血量 / 任务目标文本（你的反馈 1）

诚实说明现状：

- **可行**：GUI 绘制（`Gui.rect` / `Gui.text` / `Gui.resolution`）与**内存读取 UI 控件几何**（CD mod 读小地图即为例证）
- **未知**：血量、体力、任务目标**文本**的具体地址与结构。CD mod 完全不涉及这部分，需要单独探测
- **建议**：先用同样的方法探测，但**分成独立的小任务**，不要和倒计时 HUD 绑在一起。倒计时先跑通，血量/目标文本作为后续增量

### 3.4 采样与刷新

每 0.1 秒采样一次（与 CD mod 相同的已验证节流），**只在文本或状态变化时才重建 GUI 对象**。

## 4. 技术方案

### 4.1 代码来源：照搬 vs 重写

| 部分 | 做法 | 理由 |
| --- | --- | --- |
| 只读内存层 | **照搬** CD mod 的 reader/support | 已实测，含地址范围校验、`GetTickCount64` |
| 游戏版本校验 | **照搬并保留** | PE 头 `timestamp` + `image_size` + 6 条 RVA 特征码，这是它稳定的根本 |
| 状态机 | **照搬逻辑，重写为可读模块** | 偏移与判定已验证，但源码要能改 |
| HUD 渲染 | **重写** | 去掉小地图依赖，这是主要改动点 |
| 入口与日志 | **照搬模式**（BSL API 1、`open_log`） | 与现有 mod 一致 |

**照搬意味着沿用它的偏移常量**：

```
game + 0x3326020   → reinforcement manager 指针
game + 0x3325f18   → pacing manager 指针
m + 0xad0  float   归一化冷却比例（客户端可见）
m + 0x94   float   原生剩余秒数（仅权威端）
m + 0xa0   u32     待处理增援队列长度
m + 0xc4 + i*0x104 队列项类型（0 = 普通增援）
pace + 0x934  u32  阻塞计数
pace + 0x924  float 冷却速率
```

### 4.2 mod 形态

沿用我已建好的 **SmokeWatch 工程骨架**（构建/打包/测试链路都已验证），新增独立资源：

```
资源名 : mods/hd2mods/reinforcement_radar
入口   : 纯文本声明 + require 实现模块（必须，否则发现机制会漏掉）
实现   : 编译字节码
打包   : 双资源归档，构建期 readback 校验
依赖   : Bingus Shared Loader v15+ / API 1
```

**独立资源名，不复用 CD mod 的名字和 GUID**，两者可以共存也可以只留一个。

### 4.3 只读保证

构建期继续执行副作用 API 黑名单（`WriteProcessMemory`、`VirtualProtect`、`VirtualAlloc`、`Network.` 等出现即拒绝构建）。CD mod 只用 `ReadProcessMemory`，我的版本也一样。

### 4.4 性能

- 采样节流 0.1 秒（100ms），与 CD mod 相同的已验证节奏
- GUI 对象仅在内容变化时重建
- 每帧零分配，不做表拼接

## 8. 我不确定的地方

诚实列出，避免你在错误前提上做决定：

**偏移常量是 CD mod 的经验值，不是我推导的。** 它们的正确性由 CD mod 在你机器上跑通来背书，但我不理解 `rate` 为什么是 0.963（不是 1.0）。这个数直接参与秒数计算（`seconds = ceil(raw_remaining / rate)`），所以**如果它的成因没搞清，倒计时在极端参数下可能有偏差**。先作为观测项记录，不假设语义。

**任务目标面板的偏移未知。** 小地图的 `global_rva` / `map_widget` / `panel` 偏移是 CD mod 给出的，但任务目标面板的对应偏移没人给过。要精确贴合它，我得先做一次探测。**这是 3.2 第二步的前提**，不影响第一步先看到倒计时。

**血量与任务目标文本的地址完全未知。** CD mod 不涉及这部分。可行（GUI 和内存读取都证明了），但需要独立探测，且失败概率高于倒计时——因为不知道这些值是以什么形式存活的。

**特征码校验是版本锁。** 游戏一旦更新，6 条 RVA 特征码极可能失配，那时我的版本和 CD mod 会同时失效。这是这类 mod 的固有代价，不是能绕过的设计问题。我的应对是**快速失败**：校验不过就静默隐藏并写明确日志，绝不用错数据画倒计时。
